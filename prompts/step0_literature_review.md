# 4. Directives & Constraints (纪律与硬性约束)

- **Core Directives (核心任务与执行规范)**:
  1. **读懂评测**：读评测代码，确定输出契约（标准答案 / 单测 / 精确匹配，还是 LLM 裁判、rubric、胜率）、题型与终答形式、是否带 system prompt 或 few-shot、生成上限。后面的检索与筛选都以此为准。
  2. **反查最强公开方案**：找出目标基准（或同族基准）上，与 `{{MODEL}}` 同量级的模型公开过的最强 3–5 个后训练方案。来源包括技术报告、带 SFT 结果的数据集论文、模型卡、开源训练仓库与配置（含主流训练框架为同尺寸模型给出的示例配置）、复现或比赛 writeup；另查目标基座同家族模型的模型卡与 `generation_config.json`。每个方案按下列字段抽成一份完整配方，原文没写的字段写「未报告」：
     - **结果**：基座与尺寸、目标基准分数、出处。
     - **数据**：来源、规模、构造或生成方式（如用到生成模型，写明是哪个模型、prompt 从哪来）、过滤与筛选规则。
     - **训练**：方法与阶段顺序（全参 / LoRA、SFT / 偏好优化 / RL 等）、学习率与调度、epoch、有效 batch、总步数、序列长度、GPU 数。
     - **推理**：解码参数、生成上限。
     - **选模与后处理**：checkpoint 选择、合并等。
     - **消融**：作者报告的哪些改动带来多少收益、哪些无效。
  3. **调研数据候选（分数优先）**：在反查结果之外，按以下检索路线补全候选池，合并后再排序：
     - **按任务关键词检索**：数据集、论文、综述。
     - **沿强模型反查**：找出近 12–18 个月在同类任务上最强的开源模型（优先与 `{{MODEL}}` 同量级、从 Base 起训的），读其技术报告 / 模型卡的 post-training 数据章节，列出随模型开源或明确使用的 SFT / RL 数据集与子集。
     - **沿代际追新**：对每个经典数据集，查有没有更新一代、在同一任务上与它正面对比并胜出的后继数据集。默认新一代优先，除非有反证。
     - **逐个翻开放后训练数据的机构页**：用 HF API 按社区验证度列出持续开源后训练数据的机构的数据集，例如 `curl -s "https://huggingface.co/api/datasets?author=<org>&sort=likes&direction=-1&limit=100"`（也可 `sort=downloads`，或用 `search=<领域词>` 代替 `author`），org 例如 nvidia、allenai、open-thoughts、open-r1、HuggingFaceTB、a-m-team、Qwen、deepseek-ai 等。likes / 下载量高说明被社区大量复用和验证；新发布但几乎无人使用、也没有定量结果的数据放在后面。
     - **把每个候选拆成「prompt 来源 × 答案来源」两部分分别调研**：
       - **prompt 来源**：与评测的任务类型、语种、难度分布是否一致。评测分布从评测代码与基准的公开说明（论文、博客、数据卡）获得，不读测试集。
       - **答案来源**：答案由谁生成或校验，以及该来源在目标基准（或最接近的基准）上的公开水平。公开数据集的答案来源是其生成模型；本机生成的答案来源是可部署的开源模型。
       - 候选池必须同时包含「直接使用公开数据的答案」和「用本机可部署模型重新生成答案」两类，按同样的字段写出来，不能只调研一类。本机生成类至少比较 3 个可部署的生成模型（通用模型与领域专用模型都要查），写出各自在目标基准或最接近基准上的公开分数、单卡显存需求（按 `nvidia-smi` 估算，可用官方量化版本）与生成吞吐；prompt 来源同样要调研并说明配比。
  4. **候选排序依据**：
     - **答案来源的水平**：模型能学到的上限受答案来源约束。对候选池里的每个答案来源（公开数据集的生成模型、本机可部署的生成模型），查出比如模型卡上它在目标基准本身上的公开分数，比较各候选答案来源在目标基准上的水平；可校验任务还要看答案是否经过校验。
     - **有效条数**：预期分数由答案来源的水平和能拿到的有效条数共同决定。公开数据看现成规模（按过滤规则筛完后还剩多少条）；本机生成按生成模型的吞吐估算能产出多少条合格样本。条数是否足够，参照反查到的「规模–分数」证据判断。
     - **与评测同形、分布一致**：题型、选项数、终答形式、难度、语种与任务类型的覆盖与评测一致的数据作主干；不同形的数据只能做补充。
     - **可归因的直接证据**：公开数据看「同量级 Base 模型只用该数据训练后，在目标基准或同族基准上的分数」；本机生成看答案来源模型自身在目标基准上的分数，以及反查方案中用相近来源蒸馏得到的结果。两类证据形式不同，不能因为生成类没有训练后分数就排在后面。
     - **数据质量信号**：带逐样本质量信号（同题多解、校验结果、单测通过率、打分等），便于后续筛选。
     - **训练规模可复现**：先按 `skills/post_train/recipe_guidelines.md` §3 估算本预算可训练的条数（依据 `{{MODEL}}` 参数量、`nvidia-smi` 的显卡型号与数量、剩余墙钟、候选数据的平均长度），把算式写进产物。亮眼分数来自远超该量级的样本或多阶段完整管线时，在本预算下要打折。
     - 第 1 位就是预期最终分数最高的组合，追求高分优先，不因下载或生成更费时而降级。本机 HF 缓存（`$HF_HOME/hub`，先 `ls` 查看）只用来减少下载耗时，不作为排序优势。若第 1 位需要本机生成，第 2 位放一个可直接使用的公开数据作兜底。
  5. **横向归纳**：对比反查到的方案，写出：
     - 多个方案共同采用、或有消融支持的做法，以及对应的数值范围与出处；
     - 方案之间的分歧，以及各自成立的条件；
     - 在本 run 的约束下，哪些做法可以直接复现、哪些要调整（如把闭源生成模型换成本机可部署的开源模型、把多机配置换到单机）、哪些做不了。
     - 由此给出本 run 的推荐方案：主干数据与数据量、数据构造流程、训练配置、解码设置、后续阶段的方法。学习率等训练数值要连同其有效 batch 与步数一起写，供下游判断能否照搬。
  6. **失败现象反查**：检索与 `{{MODEL}}` 同量级的模型在这类任务上公开报告过的失败现象，以及修复办法、数值与出处。
  7. **边查边记**：开工 10 分钟内在 `{{CONTRACT_PATH}}` 写出第一版草稿（哪怕只有初步候选），之后每完成一个方案的抽取或一项归纳就更新一次，避免超时丢产物。每个数值都注明出处；找不到的写「未找到」，不要凭经验补数。
